# Lego Flow Messaging Module Standards

## Trigger

Auditing, aligning, fixing, or creating a messaging protocol module under `messaging/` (MQTT, STOMP, NATS, XMPP, Kafka, WAMP). The task involves documentation compliance, testing patterns, interop infrastructure, or protocol flow listeners.

## Always-On: Transport Contract Audit

Any work touching a protocol module's transport, frame codec, or reader loop (new transport, transport redesign, interop failure fix) MUST audit all three parts of the byte→frame contract before changing anything:

1. **Reassembly** — a codec that does one `transport.receive()` + one `decode()` per read silently drops coalesced frames and cannot decode frames split across reads. The codec must keep a reassembly buffer and return exactly one complete frame per call.
2. **-1 semantics** — the transport SPI returns `-1` on close AND on timeout. A reader loop that treats every `-1` as connection loss kills live idle connections after one read timeout. Disambiguate with `isOpen()`: `-1`-while-open = idle, keep waiting. House pattern: AMQP `pollFrame` treats a short read as "no frame, try again". Closing-peer side: an in-memory transport must drain its queued inbound bytes BEFORE reporting EOF on `close()` — otherwise the peer's final control frame (e.g. a `-ERR` auth rejection) is silently dropped and the failure becomes a nondeterministic timeout race.
3. **Partial-read ordering** — an in-memory transport whose read partially consumes a queued buffer must hold the remainder at the stream HEAD (like TCP), not re-queue it at the tail of the pending-send queue. A tail re-queue rotates the byte stream whenever two sends are in flight, and a frame split across reads reassembles in the wrong order; unit tests that read a whole buffer in one call never see it.

## Always-On: Generic Transport Abstraction (service/channel)
All messaging modules share the same byte-level transport infrastructure. Do NOT copy implementations between modules — use the generic classes in `service/channel/`:

| Generic Class | Use When |
|---------------|----------|
| `ByteTransport` | New transport SPI — protocol interface extends this |
| `InMemoryByteTransport` | In-memory testing where partial reads re-queue at tail (AMQP, STOMP, MQTT style) |
| `InMemoryByteHeadBuffer` | In-memory testing where partial reads hold remainder at stream head (Kafka, NATS, XMPP style) |
| `PipelineByteTransport` | Pipeline over `DataChannel` with ring buffer — protocol-specific Pipeline class extends this |

**TCP semantics (InMemoryByteTransport):** The base `InMemoryByteTransport` supports configurable TCP-like behavior via `withTcpSemantics(TcpSemantics)`. Enabled by default — each `send()` is split into 256-byte chunks to simulate TCP segmentation, and `receive()` delivers one chunk at a time to simulate partial reads. Disable with `TcpSemantics.NONE` for raw synchronous queue semantics. Other modes: `COALESCING` (16 KB chunks) and `BACKPRESSURE` (bounded queue with blocking send).

**Protocol interface pattern:** Each protocol defines its own interface (e.g. `KafkaTransport`) that extends `ByteTransport` and adds protocol-specific methods (e.g. `getChannel()`). This preserves type-safety for downstream consumers while sharing implementation.

**Protocol interface cleanup rule:** If a protocol interface adds ZERO methods beyond `ByteTransport` (i.e. it is empty except for the `extends ByteTransport` clause), DELETE the interface and replace all usages with `ByteTransport`. Empty interfaces add no value and create unnecessary indirection. The only exception is when the interface is referenced in a public API where removing it would break consumers — in that case, keep it with a javadoc noting it is a marker interface.

**Implementation pattern:** Protocol-specific transport implementations extend the generic base class. The `implements ByteTransport` clause is REDUNDANT when the base class already implements it — omit it to keep the code clean:
```java
public final class InMemoryKafkaTransport extends InMemoryByteHeadBuffer {
    // protocol-specific methods delegate to super or implement directly
}
```

**Pitfall — generic base classes must NOT be `final`:** The base classes (`InMemoryByteTransport`, `InMemoryByteHeadBuffer`, `PipelineByteTransport`) must be `public class`, not `public final class`. A `final` modifier prevents extension and causes compile failures in all messaging modules.

**Pitfall — InMemoryTransport.createPair() must set peerRef:** The `peerRef` field in `InMemoryByteTransport` is `protected` (not `private`) specifically so subclasses can set it. Every protocol-specific `InMemoryTransport.createPair()` must set `peerRef` on both ends of the pair — failing to do so breaks bidirectional communication (sends on one end never reach the other). The correct pattern:
```java
var a = new InMemoryTransport(q1, q2);
var b = new InMemoryTransport(q2, q1);
a.peerRef = b;
b.peerRef = a;
return new InMemoryTransport[]{a, b};
```
Do NOT use `InMemoryByteTransport.createPair()` and cast — the returned instances are `InMemoryByteTransport`, not the protocol-specific subclass, causing `ClassCastException`. Always construct the subclass directly and set `peerRef` manually. This bug was discovered when AMQP `InMemoryTransportTest` tests failed with `BufferUnderflowException` because data sent on one end never arrived on the other.

**Pitfall — InMemoryMqttTransport.createPair() also had missing peerRef:** The MQTT module's `InMemoryMqttTransport` (which extends `InMemoryByteTransport`) had the same bug — `createPair()` returned instances without `peerRef` set, causing all multi-client MQTT tests to hang with `TimeoutException`. The fix was identical: construct both ends explicitly and set `peerRef` on each. This was discovered when `MqttClientTest.testSubscribeAndReceive()` and 31 other MQTT tests failed with timeouts. The broker's virtual thread calling `transport.receive()` had no peer to trigger the client's read loop, so the client blocked forever waiting for CONNACK.

**Pitfall — PipelineByteTransport.send() must enqueue, never write directly:** The generic `PipelineByteTransport.send()` must enqueue to `outboundQueue` and let the selector thread write via `onWrite()`. Writing directly to `channel.write()` from the calling thread races with the selector's read/write and causes message loss (confirmed by NATS/STOMP/MQTT test failures). If a protocol needs fast initial writes, handle it at the codec or protocol layer — never in the transport SPI. Also, `send()` must consume the caller's buffer by advancing position to limit after enqueuing a duplicate.

**Pitfall — PipelineByteTransport.receiveWithTimeout() must be loop-based:** The method must continue reading until the buffer is full or timeout expires, NOT return early when `count > 0`. A fast-path early return breaks tests that expect the method to wait for more data when the buffer has partial data. Use the loop pattern from the original `PipelineKafkaTransport`: check deadline, fast-path if `peek() >= buffer.remaining()`, otherwise acquire semaphore and retry.

**Pitfall — verify pre-existing test failures before claiming regression:** After a transport refactor, run the messaging test suite and compare against the committed HEAD baseline. Some failures may pre-exist and are not regressions. Use `git checkout <commit>` (detached HEAD) to run tests on a prior state rather than `git stash`, which can leave unmerged state if the working tree has conflicts. If `git stash` is used and restore fails with merge conflicts, use `git checkout HEAD -- <file>` to restore the conflicted file rather than attempting to resolve them — the stash entry will be dropped automatically.

**Pitfall — service layer must expose event listener for test synchronization:** When tests need to synchronize with protocol events (e.g., waiting for handshake completion), the service layer must expose a `setListener()` method that forwards to the underlying container/broker. Without this, tests cannot attach `CountDownLatch`-based listeners to protocol events. Pattern:
```java
// In XxxContainerService:
public void setListener(XxxEventListener listener) {
    if (container != null) container.setListener(listener);
}
```
Then in tests:
```java
CountDownLatch latch = new CountDownLatch(1);
server.setListener(AmqpEventListener.latchOnFirst(latch, AmqpEventListener.EventType.CONNECTION_OPENED));
client.connect(ctx);
assertThat(latch.await(10, TimeUnit.SECONDS)).isTrue();
```
This replaces unreliable `Thread.sleep()` waits with event-driven synchronization. The event fires only after the protocol has fully processed the client's handshake, so the test knows exactly when the connection is ready.

**Pitfall — when removing empty protocol interfaces, update ALL usages systematically:** A grep for the old interface name across the entire module (excluding `target/`) will find all references. Use a script to replace all occurrences: `find <module> -name '*.java' -not -path '*/target/*' -exec sed -i '' 's/\bOldTransport\b/ByteTransport/g' {} \;`. Then add the `ByteTransport` import to any file that uses it but doesn't already import it. Verify with a clean compile before running tests.

**Pitfall — missing imports after interface removal:** When replacing a protocol interface with `ByteTransport`, test files that reference the old interface name may be missing the `ByteTransport` import. After bulk replacement, run `mvn test-compile` to catch these — they won't surface until test compilation.

**Pitfall — protocol-specific transport classes must implement the protocol interface:** When a protocol defines a transport interface (e.g. `MqttTransport` extends `ByteTransport` with `getChannel()`), the protocol-specific pipeline transport class (e.g. `MqttPipelineTransport`) must declare `implements ProtocolTransport` even when extending the generic base class. The generic base (`PipelineByteTransport`) implements `ByteTransport` but NOT the protocol interface. Without this, Gradle compilation fails with "incompatible types" when code assigns the pipeline transport to the protocol interface type. This applies to any protocol interface that adds methods beyond `ByteTransport` (currently only `MqttTransport` with `getChannel()`).

**Pitfall — interop tests should use `@Disabled` instead of property-based skip:** Use `@Disabled("Requires external <service>: docker compose -f interop-tests/docker-compose.<group>.yml up -d")` on interop test classes rather than `skipInteropTests` property. This ensures both Maven and Gradle discover the same tests and report identical skip counts. Property-based skip (`skipInteropTests=true`) causes Gradle to exclude test sources from compilation entirely, making them invisible to test discovery while Maven still compiles and skips them — resulting in different test counts between build systems.

**Pitfall — generic base classes may need protected members for subclass override:** When a protocol-specific transport needs to override `receiveWithTimeout()` with different semantics (e.g. simple semaphore-wait vs. loop-based fill), the generic base class must expose its internal semaphore as `protected`, not `private`. `PipelineByteTransport.available` was changed from `private` to `protected` for this reason. Without this, subclasses cannot access the semaphore and cannot override the method.

**Pitfall — demos module also needs updating when interfaces are removed:** The `demos` module references protocol transport interfaces directly (e.g. `KafkaTransport`, `StompTransport`) and is not covered by module-level bulk replacement. After removing empty protocol interfaces, grep the demos module for remaining references: `grep -rn "KafkaTransport\|StompTransport\|AmqpTransport\|NatsTransport\|XmppTransport" demos/src --include="*.java"`. Replace with `ByteTransport` and update field types/method signatures accordingly.

**Pitfall — Maven and Gradle must produce identical test results:** The user requires `mvn test` and `./gradlew test` to report the same test counts, failures, and skips. A discrepancy indicates a build-system mismatch in test discovery or dependency configuration. Common causes:
- Gradle missing dependencies that Maven resolves via the parent POM (e.g. `lego-flow-kafka`, `lego-flow-wamp`, `slf4j-simple` in interop-tests)
- Gradle excluding test sources from compilation while Maven compiles and skips execution
- Different test discovery: Maven Surefire reports `@Nested` test classes separately; Gradle JUnit Platform merges them into the parent suite (same total, different suite count)
- Stale Gradle test XML: verify `build/test-results/test/*.xml` mtime is newer than the run start before citing counts

Fix: add missing dependencies to `build.gradle.kts`, remove compile exclusions that prevent test discovery, and use `@Disabled` annotations (not property-based skip) for interop tests so both systems discover and report them identically.

**Pitfall — Gradle test results use different format than Maven:** Maven uses `target/surefire-reports/*.txt` with `Tests run:` format. Gradle uses `build/test-results/test/TEST-*.xml` with `tests=".." failures=".." errors=".."` attributes. To get Gradle test counts, parse the XML: `find . -path "*/build/test-results/test/*.xml" -name "*.xml" | xargs python3 -c "import xml.etree.ElementTree as ET; import sys; ..."`. A quick grep like `grep -h "Tests run:"` will return empty for Gradle. Also verify XML mtime is newer than the run start before citing counts — stale XML from a previous run makes a test suite that never ran look green.

## Always-On: Headless Audit (run before committing a compliance migration)

The whole point of the migration is that the protocol core owns no sockets. Verify it with a grep, not by trust, before you commit — the core packages must return ZERO hits and the service layer must be the only socket-owning code:

```bash
# protocol core packages must return ZERO hits:
grep -rn "import java.net.\|SocketChannel\|ServerSocket\|new Socket\|Selector" \
  messaging/<module>/src/main/java/<core packages>/ | grep -v "service/"
# the service layer MUST be the only socket-owning code (expect hits here):
grep -rln "SocketChannel\|ServerSocketChannel" messaging/<module>/src/main/java/<service packages>/
```

A clean core + a service layer that owns all sockets is the acceptance criterion. If the core still has socket references, the migration is incomplete — do not commit.

## Always-On: Compact Verified Increments (how migrations actually ship)

The user's standing rule: **do NOT hand a big unverified overhaul to one actor.** A subagent (or a single giant pass) that "overhauls" many files without producing results burns the turn on recon and self-reports partial. Instead, decompose the migration into compact increments and execute them in order, each verified before the next starts. This is what keeps both context and progress honest.

The increments for a headless compliance migration, in order: (1) headless server — strip sockets, add `handleConnection(transport)` + read loop; (2) transport-injected client ctor + read loop; (3) service layer — the only socket-owning code; (4) new tests — transport + server + real-TCP integration; (5) coverage ≥80% gate; (6) demos/interop compile; (7) docs; (8) commit. Track every increment in a todo list so "what is still left" is always knowable — the user explicitly wants to see the remaining work, not a monolithic "working."

Request-response modules (Kafka) shape the increments differently:
- **Multiple public client entry points** (Kafka: `Producer`, `Consumer`, `AdminClient`) ALL become transport-injected — the `(host, port)` constructor on each is replaced with a transport constructor, not just the low-level `KafkaConnection`. Their unit tests migrate from real-TCP to in-memory pairs.
- **The headless server's `handleConnection(transport)` runs the connection read loop on the broker's virtual-thread executor**, not synchronously on the caller's thread — a synchronous loop blocks the service layer / test the instant it calls `handleConnection` (NATS's `NatsServer.handleConnection` spawns one per connection the same way).
- **A large broker is a monolith with a small socket surface** (KafkaBroker is 1000+ lines): only the accept loop, `handleConnection`, `readFully`/`writeFully`, the server-channel field, the `start()` bind, and `close()` are socket code. The request handlers are pure protocol logic — leave them untouched and refactor only the socket surface.

Rules:
- **Verify each increment before the next** — compile + run the module test suite after each, so a failure is isolated to the increment that caused it. Do not stack unverified changes.
- **Keep the main context lean** — check file size before reading; prefer targeted greps for API surfaces (signatures, public methods) over whole-file reads; for compile steps verify with targeted builds (`mvn test-compile -pl <module>`), not by re-reading every file.
- **Subagents are an option per-increment, not the whole migration.** If you delegate one increment, write the bounded spec to `doc/plans/messaging/PHASE<N>_<PROTOCOL>_SPEC.md`, have the subagent read it, and require machine-verifiable handles back (test run/failed counts, build exit codes, raw-socket grep) — then confirm those numbers in the parent before committing. A self-reported "done" with no numbers is unverified work.
- **Stop a stuck subagent and take the work over directly** in compact increments rather than waiting on a monolithic result.

## Always-On: Versioned Codec Discipline (user-corrected workflow)

Building versioned protocol codecs (Kafka today; any protocol whose messages carry per-version wire layouts) follows these standing rules — the user corrected the opposite behavior explicitly:

**Kafka status (2026-10-24):** All 37 APIs have dedicated codecs. Phase 6a is COMPLETE. Phase 6 Kafka interop tests are COMPLETE (trivial + multi-partition + transactions). Phase 6 WAMP interop tests are COMPLETE (session + pub/sub + RPC + multi-realm). Phase 7 guidelines are COMPLETE. See `references/unpin-negotiated-version.md` for remaining negotiation gaps.

1. **Spec per version is the source of truth** — layouts come from the per-version spec docs/JSON in the module's `doc/spec/` (field order, types, presence). Wire captures may VALIDATE interop, but never DERIVE a layout. Do not build or justify a field order from a captured byte stream, and do not spend the turn on broad preliminary verification before implementing + unit-testing the small piece. A GREEN round-trip suite does NOT prove version accuracy: round-trips through your own encoder are self-consistent, so a baseline can ship the latest-version field order under a v0 label with every test still passing — only spec-derived exact-byte vectors detect it. When picking up an existing `encodeXxxV<N>`, re-derive its layout from the spec before extending it. The module's `doc/spec/*.json` files open with a `//` license-comment block, so they are not strict JSON — strip the lines whose stripped form starts with `//`, then `json.load` works; walk each field's `versions` range to confirm the exact per-version delta (a field can be `2+` in the response while its request-side sibling only appears in `3+`). For Kafka, materialize the spec artifacts first with the module's `gen_kafka.py`: `freeze <API> <Request|Response>` writes the frozen order tables (`doc/spec/order/`), `delta <API> <vN> <Request|Response>` prints the per-version delta (a missing version argument fails SILENTLY with empty output — verify output is non-empty before treating a version as unchanged); command set in `references/per-version-codec-discipline.md`.
2. **Split by API sub-category into several small classes** — one codec class per API (or sub-category) with a thin delegating facade; never extend one big monolith codec. Unit tests stay small and grouped in one test class per sub-category. Test the small files, not the monolith.
3. **One dedicated-codec API per sub-task (all versions, one commit); implement versions in order v0 → latest** — settle one API at a time: the dedicated codec class + one test class + one code commit covering ALL its versions (v0–v3, v0–v9, …), with one matrix row per version, all settled by that single commit — that is the established house form for the recent rows, and a whole-API row stays self-contained (one green tree, no return to already-done work) — the code commit must contain BOTH the new dedicated codec AND the one-line delegate in the thin facade that routes to it; leaving the delegate out means the facade stays modified in the tree and the row looks unfinished on every resume. Before rewiring, confirm the version the delegate routes at: the pin comes from the ApiKey table + the client/broker call sites, NOT from the old inline facade body — the inline body may encode a NEWER version than the pin (wire mismatch), so the dedicated codec must encode the pinned version exactly, which can CHANGE the facade bytes; first verify the existing facade tests are round-trip + field assertions only (no golden bytes) before touching the layout. Within the implementation, still write v0 first and verify before moving on — a red v0 blocks v1…latest. Only when a row extends a SHARED codec one version at a time, use the older form instead: one version per sub-task, each committed on its own green tree, never two versions in one sub-task.
4. **Choose the mechanism as part of that version's implementation** — a version byte-identical to the previous one (verify against the spec JSON, not memory) shares the previous version's methods via a fall-through `case 0: case 1:` plus a javadoc note; a layout-divergent version gets dedicated methods (e.g. `encodeResponseV1`/`decodeResponseV1`). When only ONE direction diverges (a request-only or response-only version), the diverging direction gets the dedicated `V<N>` methods and the unchanged direction's dispatch routes to the previous version's methods (e.g. response `case 15` → the V13 response methods) — verify the unchanged side by diffing the two versions' field orders (a frozen order table or generator `order` output for N-1 vs N), and state in the commit subject + progress entry which direction changed and that the other is wire-identical. When version N lands, ALSO re-pin the version-dispatch `assertThrows` tests to the next unimplemented version — cover all four entry points (encode/decode × request/response = 4 tests) so the next line's dispatch is already asserted. Record the mechanism choice in the commit message + plan progress log + requirements entry. When the version adds a model field, extend the record WITH a compat constructor defaulting the new field — do not rewrite every older call site: `references/per-version-codec-discipline.md` ("Evolving the model record when a version adds fields").
5. **Dual-case decisions: choose fast, record the rejected alternative, reuse it.** Standing user rule: on an A/B fork (wire-order ambiguity, absent-vs-default encoding, layout alternative) spend limited consideration on the "best" option and commit to it — never loop re-evaluating; a recurring problem must end in a decision. Record the rejected alternative where interop will find it: an `INTEROP NOTE` paragraph in the commit message stating the alternative and the concrete fix if a real broker disagrees (e.g. "read tag X into the model; encoder unchanged"). For very similar cases in later rows REUSE the earlier decision without re-deriving it — the recorded note is what makes the final fix cheap during the interop phase, and re-evaluation is how rows drag on.
6. **Track in the code / generator+spec / docs+matrix commit split** — commit the Java code+tests first; if the version work ALSO touched the generator or spec docs (a structural branch the generator must encode, a new `gen_kafka.py` CLI command, a new spec section, or new frozen order tables), commit those SEPARATELY next — the user directs code and generator/spec changes as distinct commits, never merged; then a docs-only commit that marks the matrix row ✓ with the CODE commit's short hash (the matrix's Commit column records it, so it cannot go in the code commit itself), prepends the progress doc's log entry (newest-first, with the "was N tests" baseline recorded), and appends the requirements entry. A sub-task is only done when its matrix rows are marked. When the docs are drafted BEFORE the code commit, the code commit's SHA is unknown — write an explicit `PENDING` placeholder in every SHA slot (matrix Commit column, progress log entry, requirements heading) and backfill the real short hash in the docs commit; the standard docs commit subject is exactly that backfill ("docs — backfill <API> commit SHA <hash> into matrix/progress/requirements"). A crash between the two commits leaves precisely that state (uncommitted code+docs, `PENDING` markers), and recovery is: verify the uncommitted code (module suite), commit it, grep the module docs for `PENDING` and replace with the real hash, commit the docs — the placeholders ARE the resume state; do not re-derive it.
   - **Commit-message numbers must be verified, not eyeballed** — state the NET test delta (added − removed; a version that adds 6 methods and removes 2 stubs is "+4 net", not "+6") by grepping the commit diff (`+.*void ` / `-.*void `), and give the full-module total the same way (baseline → new). A wrong count in one commit message poisons every later row that quotes it.

## Always-On: Durable Checkpoints and Session Recovery (user standing rule)

Long tasks (version rows, migrations, interop) span session boundaries — context compaction, IDE restart, or a provider failure destroys anything that lives only in the conversation. Standing user rule: save accumulated findings FREQUENTLY in a compact structured form with per-item confidence levels, so a resumed session needs minimal re-derivation.

- **Checkpoint file lives in the repo, not the conversation** — per module doc/ (e.g. `messaging/<module>/doc/CODEC_GEN_CHECKPOINT.md`): a status table (item → state + commit hash), each finding tagged with an assurance level — `absolute` / `verified` / `under-investigation` / `rejected` — plus a next-item pointer. Also a log entry in the plan's progress doc (`doc/plans/.../PROGRESS.md`), and commit both so they survive repo resets. A fact that exists only in the conversation does not count as known.
- **The checkpoint carries the verified content itself, not just status** — for codec work: the per-version byte vectors/lengths, the version pin, the confirmed model accessors, and the decision notes (rejected alternative + fix-if-broker-disagrees). A resumed session must be able to generate code and tests from the checkpoint alone — if a fact needs re-grepping before writing code, it was not recorded, and the re-derive loop the user flags is exactly the compaction loop the checkpoint exists to kill. Record vectors at verification time, while the hex dump / probe output is fresh in front of you — a vector recalled after compaction is the thing a resumed session then wastes a turn "re-verifying" by re-deriving.
- **Update the checkpoint at each finished item, not at session end** — a mid-work loss then costs at most one item instead of the whole run.
- **Record a design reversal in a settled doc, not just the checkpoint** — when the work pivots and rolls back an earlier approach (e.g. extended protocol records reverted to a compact v1 shape), write the decision + reason into a `doc/work/<AREA>_SETTLED.md` (or the module's decision log) in the same increment: without it, a resumed session — or the user reading a diff — sees the tree contradicting the plan and has to re-derive why "changed then unchanged" was intentional.
- **Ledger cadence is per sub-task, not per session** — open a fresh WIP ledger at the START of every sub-task (not only at session start) and mark it over the instant the sub-task finishes; a mid-sub-task crash then costs at most the one sub-task instead of the whole run. After a sub-task completes, COLLAPSE the ledger to a short "last completed step" summary (the one-liner of what was just done plus the next step) before filling it again — the long accumulation of every intermediate state is exactly what bloats the ledger and defeats its purpose.
- **The ledger is the in-flight list, and it stays out of the settled file** — a ledger records ONLY work still in flight; settled facts move to the settled doc (`doc/work/<AREA>_SETTLED.md`) as they land so the ledger stays small. After any session interruption (compaction, IDE restart, provider failure) read the ledger FIRST — before any re-derivation — and re-verify only its live anchors (git status/log, the module test count, the referenced file paths), because the ledger's existence claims can go stale (a file can be renamed, a branch rebased) after an interruption.
- **Anti-compaction-loop rules** — the failure mode this exists for: after a context loss the session re-derives the same state (git status, diffs, re-reads of already-read files) over and over instead of implementing, and each re-read consumes context and triggers another compaction. Cap: ONE discovery pass per resumed session; if you catch yourself re-reading state already verified, stop and WRITE. Redirect bulky terminal output to a file (`> /tmp/x.txt`) and read it back with read_file — inline output can collapse under compaction, file contents do not. When a terminal result comes back EMPTY (...[truncated]
- **Re-verify the summary's existence claims by symbol grep before rewriting anything it calls incomplete** — the "summary text drifts" rule above extends from numbers (counts, hashes) to completeness claims. A summary is written from a truncated read (read_file cuts at its character budget, mid-method) and reports what it never reached as missing: a method lower in the file becomes "never written", a complete encoder becomes "half-finished/buggy". `grep -n` the exact method name and dispatch `case` label and read what is actually there before deciding what is genuinely missing — trusting the summary's existence claims double-implements working code.
- **Recovery procedure** — on resume: read the checkpoint (the in-flight WIP ledger FIRST — it says exactly where the last sub-task stopped, so no re-derivation) → verify only its live anchors (git log/status, the module test count, and that the referenced file paths still exist) → resume at the TODO row. Do NOT re-derive state from a truncated transcript before reading the ledger. If the checkpoint is missing, recover the prior transcript from the session store with `sqlite3 ~/.hermes/state.db "SELECT id, role, content FROM messages WHERE session_id='<uuid>' ORDER BY id"` (messages columns: id, role, content), then distill it into a new checkpoint file instead of re-deriving state. Pull authoritative numbers (test counts, commit hashes, mechanism choices) from the repo's progress log and commit messages, not from the recovered conversation — summary text drifts.
- **Re-verifying already-green, unchanged work is the restart trigger, not diligence** — if the sub-task's code+tests were already verified green earlier this session (module suite green, the dedicated test class green) and the files have NOT changed since, do ONE bounded state check (git status + a grep for leftover `PENDING`/`IN FLIGHT` markers) and then EXECUTE the single missing step (usually the code/docs commit). Re-running a green suite on unchanged files burns context, triggers another compaction, and is exactly the "spending too much effort uselessly" loop the user force-restarts the agent for. Pitfall 19c's "verify it" means: re-run the suite only if the tree changed since the last green run; unchanged ⇒ trust the prior green and commit.

## Build Environment

No `mvnw` wrapper in the repo root (there IS a `gradlew` — AGENTS.md pre-approves `./gradlew test`) and no system `java`/`mvn` on PATH — a fresh terminal cannot run Maven until you export:

```bash
export JAVA_HOME=$HOME/.sdkman/candidates/java/current
export PATH=$JAVA_HOME/bin:$HOME/.sdkman/candidates/maven/current/bin:$PATH
```

Verify `java -version` reports JDK 25. When the network is unavailable, add `-o` (offline) to every mvn invocation — the full dependency set is already in `~/.m2`.

**Whether the export persists depends on the platform**: on the local Mac (Acp mode) the shell env does NOT persist across `terminal` calls — prefix every mvn invocation in the same call: `export JAVA_HOME=... PATH=... && mvn -q -o test -pl <module>`. On the CI/devbox it may persist. If `mvn: command not found` appears, the env did not persist — re-export inline rather than assuming the session state. A quiet build (`mvn -q test`) prints nothing on success — confirm pass counts by reading `target/surefire-reports/*.txt` (grep `Tests run`) after the build, not by trusting exit code 0 alone, and cite those numbers in commits/progress logs. When `mvn` is unavailable and you fall back to `./gradlew :<module>:test` (pitfall 2 — project names are `:lego-flow-<module>`, a wrong path exits in seconds), verify the same way: read `build/test-results/test/TEST-*.xml` (grep `tests=".." failures=".." errors=".."`) and check each file's mtime is newer than the run start BEFORE citing the counts — a fast Gradle exit means wrong project path or a cached no-op, and stale XML from a previous run makes a test suite that never ran look green.

## Pitfalls

1. **JaCoCo is Maven-only** — Gradle has no `jacocoTestReport` task. Running `./gradlew jacocoTestReport` fails with "task not found". Always use Maven `-P jacoco-coverage` for coverage.
2. **Gradle project names are `:lego-flow-<module>`** — Not `:messaging:<module>`. Run `./gradlew projects` to discover correct names before targeting a module.
3. **MqttPersistenceAdapter.MqttSessionData is a record** — Access fields via accessor methods (`data.cleanSession()`), not direct field access. Java records use accessor methods, not public fields.
4. **Subagent-generated tests are unreliable** — When subagents hit iteration caps or API timeouts, outputs are truncated/incomplete. Always verify compilation with `mvn test-compile` before running tests. Never trust a "completed" status without actually running the tests.
5. **In-memory transport pairs hide production I/O bugs** — unit tests over `createPair()` never exercise coalesced TCP segments or read timeouts. An interop multi-message test (5+ small messages against the real broker) is the canary for transport/codec contract bugs; keep it in `interop-tests/` and fix failures there instead of patching in-memory-only paths. Local combined-run recipe: `references/interop-test-migration.md`.
6. **A stale `~/.m2` snapshot jar masks a broken API** — the Maven root POM has an empty modules list, so consumer modules that are not in the same reactor build (e.g. `demos`) resolve sibling modules from `~/.m2`, not the working tree. After refactoring a module's public API, `mvn install -DskipTests -pl <module>` (or delete the stale artifact) BEFORE trusting consumer compiles — a consumer building against the stale jar reports green even when the new API doesn't exist, and the break surfaces only after the artifact is refreshed.
7. **Verify each commit's tree is self-contained before committing** — a fix commit that references a symbol added in a later commit (a codec calling a reassembly primitive that is still uncommitted) breaks every build between the two. After staging, confirm the staged set covers all new references and spot-check the committed tree with `git show <sha>:<path>`; when a fix depends on uncommitted work, commit the dependency first or `git reset --mixed` and reorder the commits.
8. **A dedicated read loop draining a shared outbound queue makes that queue a race** — when a transport-injected client adds a read loop that drains the stream's outbound queue while the sender thread still enqueues, the queue must be concurrent (`ConcurrentLinkedQueue`), not a synchronized list cleared-and-iterated. The sender writes, the loop polls; a non-thread-safe `clear()` loses in-flight stanzas.
9. **After narrowing a method signature or deleting a source file, verify with a CLEAN build.** Removing a `throws` clause (e.g. making a headless `start()` unable to fail with a checked I/O error) leaves a dead `catch (IOException)` in an unmodified caller — a compile error, but an incremental build never recompiles unmodified files, so it surfaces only on `mvn clean`. The same stale-target issue keeps a `.class` of a deleted source file around, which can show up as a phantom test error in the surefire report — and a deleted *test class* is worse: its stale `.class` still runs as a real test, and its side effects (writing fixture or capture files) can resurrect files you just `git rm`'d. Rule: after any signature change or source deletion, run `mvn clean test -pl <module>` once before trusting a green, and check `git status` for reappearing fixture files.
10. **Decide the legacy client API deliberately — remove the violating ctor, keep the clean one.** A compliance migration adds the transport-injected ctor; what it does to the old client ctor depends on whether the old ctor is itself the violation. A legacy `host/port` client constructor opens a raw socket in the protocol core — that IS what the migration removes, so it must be deleted and the downstream (tests, demos, interop) migrated to the transport-injected ctor (NATS client D7; Kafka client D11). A legacy no-arg / in-memory client constructor that opens no socket is not a violation — preserve it alongside the new ctor so demos and interop keep compiling, then verify they still compile clean after the core change. After the choice, re-run the headless audit to prove the core is socket-free either way.
11. **Surefire `systemPropertyVariables` overrides class-code defaults** — a module pom can pin properties for the forked test JVM (e.g. the interop pom pins `interop.amqp.port`), so a test's `System.getProperty(name, "5672")` fallback is a red herring: the class-code default is NOT what ran. Before concluding a test hits the wrong broker/port, read the pom's Surefire `systemPropertyVariables` block — the pom value is what the JVM actually used.
12. **Interop Docker is per-group and disjoint** — standing preference: each interop group owns one compose file (`docker-compose.<group>.yml`) with exactly the services it needs; no shared compose file with a runtime-selected subset, no cross-group containers. Splits are exact partitions of the services; validate each file with `docker compose -f <file> config --quiet` (catches invalid YAML like duplicate keys that text edits sneak in); before deleting a service, grep every test for its port — the broker that exists "for test X" often also serves interop test Y. Run commands, counts derivation and the record-only-capture removal checklist: `references/interop-test-migration.md`.
13. **Per-version field-delta generators must union request AND response field lists** — a Δ/matrix column computed from request fields only reports a response-only addition (e.g. a new trailing timestamp field) as "unchanged", silently mislabeling the plan's tracking rows. Generate each row's delta from the union of both sides' field signatures.
14. **Never mix array-index reads and buffer-method reads in one exact-byte test** — `arr[i]` does not advance `ByteBuffer` position, so the next `getLong()` reads the wrong bytes; and `getChar()` consumes 2 bytes as ONE UTF-16 char, not two ASCII bytes. Consume every data byte through buffer methods; read ASCII wire bytes with single `get()` calls. When the assertion sequence interleaves array-index spot checks with buffer reads, re-anchor explicitly with `buf.position(n)` before the next multi-byte buffer read — after the last field the position is often one byte off the expected value. See `references/per-version-codec-discipline.md`.
15. **For a version that is a framing divergence, read the protocol library's GENERATED sources, not the spec JSON** — for Kafka: extract the source jar of the reference release (e.g. 3.6.1) and read `message/ApiVersionsResponseData.java`-style generated classes for the exact field order, type widths, and tagged-field tag numbers. The spec JSON gives field names/presence but NOT: (a) int16-vs-int32 widths for flexible-version fields, (b) the wire order inside a struct (e.g. a field written before its apparent logical sibling — a real 3.6.1 quirk where `FinalizedFeatureKey` writes maxVersionLevel BEFORE minVersionLevel), or (c) which fields are non-nullable compact vs nullable compact. Generate the expected total in the test comment from the generated source's field list.
16. **A version whose wire framing diverges (flexible headers, tagged fields, compact arrays) belongs in dedicated `encodeXxxV<N>`/`decodeXxxV<N>` methods, and its tag/section sizes must be computed exactly** — see `references/per-version-codec-discipline.md` ("Kafka flexible-encoding (v3+) wire facts"). A fixed per-element byte estimate for a variable-width array (e.g. assuming 9 bytes per element of a compact-string list) silently over-allocates the tag payload size varint, making the decoder skip PAST the next tag — the encoder "works" in a self-round-trip but fails against the reference. Compute the size as `varintSize(n+1)` header + `sum(varintSize(nameLen+1) + nameLen + fixedWidth)` over the elements.
17. **An edit-approval denial is a pause signal for the in-flight sub-task, not an obstacle to route around.** Do not re-express the same change in another file, and never leave the tree half-migrated with code at the new contract while committed tests still assert the old one (the old `v1-throws` tests vs. new v1 methods is the classic instance). Revert the partial change with `git checkout -- <files>` back to the last committed green state, verify the suite is green, and report the clean stopping point; resume only when the user says to continue. First distinguish a user denial from a **client auto-deny**: a "denied by the user" result can arrive with NO prompt ever shown — the IntelliJ AgentBridge plugin that drives ACP sessions from the IDE hard-codes auto-deny, so writes to protected agent-instruction files (AGENTS.md) are answered by the client before any dialog renders, and retrying just re-denies the same request. Verify with `grep "auto-denying native tool" ~/Library/Logs/JetBrains/<IDE>/idea.log`. When the client cannot surface the prompt: do not retry, do not route the edit through terminal/shell to bypass the gate, and do not loop asking the user to approve — hand them exact manual instructions instead (⌘F search anchor + the exact current text + the exact replacement text, copy-paste ready), or offer to redo the edit in a client that renders interactive prompts (CLI or desktop chat).
18. **When a hand-computed exact-byte total disagrees with the encoder output, resolve the direction before editing either side** — do not assume the encoder is wrong (and do not assume your arithmetic is right). Dump the actual encoded hex with a scratch main and verify it field-by-field against the per-version spec layout; then fix the side that deviates from the spec. Probe recipe and the surefire-report verification step: `references/per-version-codec-discipline.md`.
19. **After a session crash/restart (IDE restart included), audit the tree before starting the next row** — the tree can be half-migrated in two shapes, or complete but uncommitted: (a) uncompilable — dispatch `case N:` wired to methods never written; (b) compilable but RED — the dispatch cases landed while the rest of the row did not, so the old dispatch tests (asserting vN throws) fail against the new fall-through — an IDE restart leaves exactly shape (b): some saved hunks, the rest lost; (c) fully complete but uncommitted — the agent finished verification and died before committing, so the uncommitted set IS the finished row: verify it (run the module suite), commit the code, backfill the `PENDING` SHA placeholders in the docs, commit the docs (pitfall 6) — do not start the next row. Run `git status` + `git diff` to see what landed, then walk the row's part checklist and finish each missing part: all four dispatch cases, the class javadoc bullet, every stale `vN+ not implemented` comment (both switches), the new version's test class, the re-pinned dispatch `assertThrows` tests, and the matrix row + progress log entry. Expect the suite RED until the parts align — do not be surprised by a failure in the OLD tests, and never layer the next version on a half-row. Persist the row's state into the module checkpoint file as you go (Always-On: Durable Checkpoints), so the next session can tell which parts landed without re-reading everything.
20. **Fuzzy-matched edits to a version-dispatch switch silently re-group fall-through `case` labels** — adding a new `case N:` to one of the encode/decode dispatch switches with a fuzzy-matched edit tool can bleed the match across the case boundary: adjacent preceding `case` labels fall into the new group (or their `return` is dropped), so every older version suddenly encodes at N's width. After editing any dispatch switch, re-read the whole switch block and confirm each case→method grouping before running the suite — the older versions' exact-byte tests are the tripwire (a total length that jumped one version-width is fall-through corruption, not a new field). Anchor the edit to include the PRECEDING `return` statement so the match cannot span the case boundary; remember the encode and decode switches are separate (and on a response-only version the request switch is untouched — verify it is unchanged too).
21. **Two row-number systems coexist — do not conflate them.** The commit-subject row ("…row 129") is the MASTER matrix row; the REQUIREMENTS/PROGRESS row ("Record I/O row 26") is the SUB-CATEGORY row within one API. A third, sub-category-local numbering also appears in the plan file's visible matrix and matches neither. When unsure which number a row is, read the module checkpoint file (`doc/CODEC_GEN_CHECKPOINT.md`) — it records both the master and sub-category numbers and is the durable source of truth; never re-derive a row number from the plan file's matrix or by assuming one row per version. Wire-identical versions SHARE a row (v13 and v14 are the same master row), so the count of versions does not equal the count of rows.
22. **Commit messages full of backticks break `git commit -m "$(cat <<'MSG' … MSG)"`** — the heredoc sits inside `$(…)​` command substitution, so every backtick in the message body is re-interpreted as a command substitution and the shell aborts with "unexpected EOF while looking for matching quote"; these commit messages quote hashes and method names in backticks constantly. Write the message body to a file and commit with `git commit -F <file>` — no shell quoting, no interpretation of the body. The hazard class is any shell-special character in the body: a single-quoted -m also breaks on the first apostrophe in a contraction (the quote terminates early, "unexpected EOF"), so a plain -m is safe only for bodies without quotes, backticks, or `$`; when in doubt, `-F`.
23. **To fix the message of an already-buried commit (commit N+1 sits on top of commit N), use the rebase edit-stop, not `-x`** — `git rebase -i <base>` with `GIT_SEQUENCE_EDITOR='sed "1s/^pick/edit/"'` stops at commit N; run `git commit --amend -F <file>`; then `git rebase --continue` replays commit N+1 on top. The `rebase -i <base> -x 'git commit --amend …'` form misfires because `-x` runs after EVERY commit in the range, not a one-off amend. Before doing this, confirm the branch is unpushed and nothing upstream depends on the range (`git rev-list --left-right --count origin/<branch>…HEAD` shows 0 behind); rewriting pushed history is a separate decision.
24. **After a patch fails on stale content, stop the piecemeal editing — do one full-file read, then a single atomic rewrite.** A failed `old_string` match (or read results that keep drifting from the patches) means the in-head copy of the file has drifted; more partial patches against it burn turns and risk further drift. Do one authoritative full-file read, apply ALL pending fixes as one `write_file` rewrite, then verify with one build/diff — not N sequential patch attempts. The rewrite is also where the temporary debug scaffolding (hex-dump helpers, scratch asserts) accumulated during iteration gets deleted — a clean file is part of the fix, not a follow-up chore.
25. **Docs-commit claims are verified against live sources, not memory** — before the docs commit, check every factual claim against its source: the pin against the codec's `PINNED_VERSION` constant (grep, not recall); the named bug/omission against the code diff (`git show <code-sha> -- <file>` — a misnamed field in the narrative is a spec error, not a typo); nullable/default annotations against the spec JSON (`nullableVersions` is independent of presence — a field can be present at v1+ and still be nullable at v0+, so "improving" a row annotation from memory flips the spec); plan matrix rows are transcriptions of the frozen order tables (dropping a nested-field expansion is an error, not a simplification); test counts against the JUnit XML; ledger existence claims ("already committed in <sha>") against `git show <sha> --name-status` / `git ls-tree -r HEAD --name-only`. A wrong ledger note is fixed in the same docs commit, and uncommitted files stay out of scope unless asked. Extends the checkpoint re-verify rule (Durable Checkpoints) from summaries to all docs and commit-message claims.
26. **Amend the code commit after drafting docs → propagate the new hash** — a `git commit --amend` on the code commit (message fix, scope change) changes its short SHA; in the same pass, before the docs commit, grep-replace the old hash in PROGRESS.md, REQUIREMENTS.md, the WIP ledger, and the matrix Commit column with the new one. A docs commit referencing a SHA that no longer exists in history poisons every later row that quotes it.
27. **File tools resolve relative paths against the current cwd, not the repo root** — the build environment requires `cd messaging/<module>` for mvn (env does not persist across calls), and while the cwd is a module subdir a repo-root-relative path in `write_file` silently creates a doubled tree (`messaging/kafka/messaging/kafka/src/…` — must then be moved back and `rm -rf`'d) and the same path in `search_files` returns "Path not found". Use absolute paths (or paths relative to the actual cwd) for file tools while the cwd is a module subdir; `cd`-ing back to the repo root does not undo a doubled tree that already exists.
28. **Splicing into dense single-line markdown and in-place doc mutation both corrupt the file** — (a) a fuzzy-matched edit tool inserting into a progress/requirements LOG (one long entry per line) can merge the new line into the adjacent entry and drop the clean one, because the match bleeds across the line boundary; (b) a doc-mutating script that opens the target in-place (`open(path,'w')`) before its transformation completes truncates the file to 0 bytes on a mid-script exception. Discipline: for log splices, anchor to an exact unique line (or drive a python3 script) and assert the before/after entry count; write the new full content to a TEMP file then `os.replace` into place (atomic) — never truncate the live file in place. If a 0-byte or mangled file results, recover with `git checkout HEAD -- <file>` (re-read the pristine copy) and re-apply the exact-match edit. The tripwire is a `grep -c` of the entry anchor after the edit — it must still be 1.

29. **Varargs call with inexact argument type.** When calling varargs methods like `assertThat(node).isIn(nodes.toArray(...))`, use `nodes.size()` not `0` for the array length. `new ClusterNode[0]` triggers "non-varargs call of varargs method with inexact argument type" — the compiler cannot infer the exact type from an empty array literal. Use `new ClusterNode[nodes.size()]` to provide an explicit type hint.

30. **CI interop tests run by default.** The `run-interop` label is deprecated — interop tests now run by default. Use `skip-interop` label to disable. The CI job condition is: `if: ${{ !contains(github.event.pull_request.labels.*.name, 'skip-interop') }}`.

31. **git stash can cause merge conflicts on restore.** When using `git stash` to temporarily save changes for comparison, the restore (`git stash pop`) may fail with merge conflicts if the working tree has uncommitted changes that conflict with the stashed changes. If conflicts occur, use `git reset --hard HEAD` to clean up rather than attempting to resolve them — the stash entry will be dropped automatically.

32. **PipelineByteTransport.send() must enqueue, never write directly.** The generic `PipelineByteTransport.send()` must enqueue to `outboundQueue` and let the selector thread write via `onWrite()`. Direct `channel.write()` from the calling thread races with the selector and causes message loss (NATS/STOMP/MQTT failures). If a protocol needs fast initial writes, handle it at the codec or protocol layer — never in the transport SPI.

33. **PipelineByteTransport.receiveWithTimeout() must be loop-based, not early-return.** The method must continue reading until the buffer is full or timeout expires. A fast-path early return when `count > 0` breaks tests that expect the method to wait for more data when the buffer has partial data. Use the loop pattern: check deadline, fast-path if `peek() >= buffer.remaining()`, otherwise acquire semaphore and retry.
